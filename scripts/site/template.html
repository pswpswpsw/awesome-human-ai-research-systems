How is this list curated?Scanned for new systems every Monday

Kept current every week

Every Monday a scheduled AI agent searches arXiv, launch announcements, the related awesome lists and GitHub for new research systems. It tests each candidate against the rules below, checks whether any excluded system has opened to the public, and opens every listed link to catch products that moved or closed. It writes a report and changes nothing. The maintainer rules on each candidate, and an entry is added or moved only when the evidence holds up.

What gets in

A system has to pass three tests on its own public pages. A researcher can use it today, with no waitlist or private preview. It was built for research work, not as a general assistant. And it does something no listed system does, so the list holds one system for each question a reader brings. A university project and a company product are judged the same way.

Where it goes

Each system is filed by what the human still rules on, not by the stage of work it serves. The part of the product that carries research judgment is the part tested. Bench is tested first, then Delegation, Standing Verdicts, Human Approval and Critique in that order, and the first match places it. An entry moves whenever a release changes how the product works.

What counts as evidence

Every boundary is a test a reader can run against the vendor’s public pages. Pages are fetched and read directly, never through a tool that summarises them. A claim found only in page source or a script bundle carries a †, and anything no public page states is marked not documented. Each value in the How they differ tables keeps the URL and the exact words it rests on, and a check on every push rebuilds the README and this page from those sources and fails if either differs from what was committed.

The full tests, the placement rules and every exclusion are in METHOD.md. How each column is filled is in CONTRIBUTING.md, and four systems are traced through a real task in WORKFLOWS.md.

Why is a system I use not on the list?

Usually for one of four reasons. Nobody has tested it yet. It failed one of the tests above: a waitlist, a general-purpose assistant, a language service, a plugin that only runs inside another agent, or a single maintainer with nothing behind the project. A listed system already answers the same question for the same reader. Or it was removed on the maintainer’s judgment.

Systems left out after a closer look are in the exclusion table, each with its reason. The weekly scan rules out more candidates than the table records, so a system missing from it may already have been looked at. Either way, open an issue with a link to it and the case for it.

Does not documented mean the product lacks the feature?

No. It means nothing we found on the product’s public pages says either way, and features behind a login stay out of view. A ✗ appears only where the vendor says the product does not do something, or where the system’s own row in the README rules it out.

Why group systems by what you still rule on, not by task?

Two tools that do the same job can leave you answerable for very different things. One screening tool’s label is the record unless you open the paper and reverse it; another’s waits for a named person to rule. The jobs above let you start from the task, and the category on each card tells you what that tool leaves you to check.

Can a system change category?

Yes. Placement follows what the product documents, so a release that adds a reviewer log, a checkpoint, or a button that applies every fix at once moves the entry. The weekly scan reopens every listed product, and a pull request that re-tests an entry is as welcome as one that adds a tool.

Why are ChatGPT, Claude or AlphaFold not here?

General-purpose assistants are not built for a particular step of research, and researchers already know them. Models such as AlphaFold predict a property of nature, so they stand in for a measurement rather than for a judgment about how the research should go, which puts them outside the definition this list starts from.

How do I suggest a system or correct an entry?

Open an issue or a pull request on GitHub, and link the vendor page your claim rests on. CONTRIBUTING.md explains how each column is filled and what evidence each kind of claim needs.

The cards are taken from the README tables, and which system sits under which need comes from the same list that builds the README’s “What do you want to do?” section. The How they differ tables come from scripts/lib/compare.js, where each value carries the page and the words it rests on. The page is built from those files, and a check on every push fails if the committed page differs from a fresh build. To change it, edit the source and run node scripts/build.js.

The full list, and the reasoning behind every placement, is on GitHub.
