How is this list curated?Scanned for new systems every Monday

Kept current every week

Every Monday a scheduled AI agent searches arXiv, launch announcements, the related awesome lists and GitHub for new research systems. It tests each candidate against the rules below, checks whether any excluded system has opened to the public, and opens every listed link to catch products that moved or closed. It writes a report and changes nothing. The maintainer rules on each candidate, and an entry is added or moved only when the evidence holds up.

What gets in

A system has to pass two tests on its own public pages. A researcher can use it today, with no waitlist or private preview, and it was built for research work, not as a general assistant. A system that takes a question, a direction, an idea or a codebase all the way to a finished paper or report must also document, on the path it is filed on and at that path’s default settings, something a reader can check: a check of its own draft against sources or runs, a gate on research content that only a person can pass, a trace tying each result to the specific run, code or passage behind it, or an exportable record of who decided. A system that finds research gaps, proposes ideas or hypotheses, or judges whether an idea is new must leave something a reader can check in the same way, such as the papers behind each gap, a test of each hypothesis against data, a check of whether a gap is still open, or the prior work behind a novelty verdict. One that hands back only a ranked list of ideas is at most a close alternative. A system that passes and answers a question no listed system answers gets its own row. One that answers the same question as a listed system joins its cluster as one line, and each cluster’s featured system is chosen by written criteria, with arrival order counting for nothing. A university project and a company product are judged the same way.

Where it goes

The page starts from the stage of the project, and inside each stage every entry is filed by what the human still rules on. Each part of a product that carries research judgment is tested on its own, so one product can have several entries in different categories. Bench is tested first, then Delegation, Standing Verdicts, Human Approval and Critique in that order, and the first match places it. An entry moves whenever a release changes how the product works.

What counts as evidence

Every boundary is a test a reader can run against the vendor’s public pages. Pages are fetched and read directly, never through a tool that summarises them. A claim found only in page source, a script bundle or a repository’s code carries a †, and anything no public page states is marked not documented. Each value in the How they differ tables keeps the URL and the exact words it rests on, and a check on every push rebuilds the README and this page from those sources and fails if either differs from what was committed.

The full tests, the placement rules and every exclusion are in METHOD.md. How each column is filled is in CONTRIBUTING.md.

Why is a system I use not on the list?

It may be here already. A system that answers the same question as a listed one appears as a close alternative, listed inside that system’s stacked card: open + close alternatives on the card it most resembles. Otherwise it usually failed one of the tests above: a waitlist, a general-purpose assistant, a language service, a plugin that only runs inside another agent, or a single maintainer with nothing behind the project. It may also have been removed on the maintainer’s judgment, or not tested yet.

Systems left out after a closer look are in the exclusion table, each with its reason. The weekly scan rules out more candidates than the table records, so a system missing from it may already have been looked at. Either way, open an issue with a link to it and the case for it.

Does not documented mean the product lacks the feature?

No. It means nothing we found on the product’s public pages says either way, and features behind a login stay out of view. A ✗ appears only where the vendor says the product does not do something, or where the system’s own row in the README rules it out.

Why start from the stage of the project?

A researcher looking for help usually knows which part of the work they are on: understanding the field and the problem, finding gaps and ideas, proposing a solution and checking it is new, designing and running the experiments, or writing it up. So the page opens there. Inside a stage, two tools that do the same job can still leave you answerable for very different things. One screening tool’s label is the record unless you open the paper and reverse it; another’s waits for a named person to rule. The category on each card tells you what that tool leaves you to check.

Why does one product appear more than once?

Some products have parts that do different jobs and leave you different things to rule on. Each such part has its own entry, with its own category, so a card always describes the part that does that job. A system sits under Hand over the whole project, and is not split across the stages, when it starts from a question, a direction, an idea or a codebase, decides which experiments or analyses to run, runs them and hands back a finished paper or report, with no documented step at which you design the experiments.

Can a system change category?

Yes. Placement follows what the product documents, so a release that adds a reviewer log, a checkpoint, or a button that applies every fix at once moves the entry. The weekly scan reopens every listed product, and a pull request that re-tests an entry is as welcome as one that adds a tool.

Why are ChatGPT, Claude or AlphaFold not here?

General-purpose assistants are not built for a particular step of research, and researchers already know them. Models such as AlphaFold predict a property of nature, so they stand in for a measurement rather than for a judgment about how the research should go, which puts them outside the definition this list starts from.

How do I suggest a system or correct an entry?

Open an issue or a pull request on GitHub, and link the vendor page your claim rests on. CONTRIBUTING.md explains how each column is filled and what evidence each kind of claim needs.

The cards are taken from the README tables, and which entry sits under which stage and job comes from the same list that builds the README’s “What do you want to do?” section. The How they differ tables come from scripts/lib/compare.js, where each value carries the page and the words it rests on, and the close alternatives in each stacked card come from scripts/lib/clusters.js. The page is built from those files, and a check on every push fails if the committed page differs from a fresh build. To change it, edit the source and run node scripts/build.js.

The full list, and the reasoning behind every placement, is on GitHub.
